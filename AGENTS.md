# Working in this Jac project

This is a [Jac](https://www.jaseci.org/) project. Jac's syntax has evolved and
is easily confused with Python or JSX -- before writing or editing `.jac`
files, consult the reference guides bundled with the compiler.

## Reference guides

The `jac` CLI ships curated reference guides ("Agent Skills") -- versioned
coding guidance for the installed compiler:

- `jac guide` -- list every available guide
- `jac guide <name>` -- print a guide (e.g. `jac guide jac-types`)
- `jac guide --search <keyword>` -- find guides by topic
- `jac guide --json` -- machine-readable output for tooling

Start with `jac guide jac-essentials`, then load the guide for your task.
Use `jac guide <name> --sections` to list headings and
`jac guide <name> --section <slug>` to retrieve a relevant section.

## Validate your work

- `jac check <file>` -- type-check and lint. Compiler diagnostics link to the
  relevant guide; follow the `-> run 'jac guide ...'` hints.
- `jac run <file>` -- execute a Jac script.
- `jac run --dev main.jac` -- serve a web-app or service in dev mode
  (hot-reload for client files; restart for server changes). Use this instead
  of `jac run` for apps.
- `jac browse <action>` -- QA a running app in a headless browser:
  `jac browse open localhost:8000`, then `snapshot` (accessibility tree with
  `@e1`-style refs), `click @e5`, `fill '#email' user@example.com`, `screenshot`, `close`.

_Generated by `jac create`._

## Commit, PR and merge policy

Read [docs/COMMIT_STYLE.md](docs/COMMIT_STYLE.md) before writing commit/PR text
or merging. Use `type<scope>: outcome`, lowercase with no final period.
Supply an explicit styled merge/squash title and reviewed body, constrain the
operation to the reviewed head, and verify the resulting message. Reuse existing
issue PRs and keep drafts until current-head/current-base acceptance passes.

## CI scope

Adding any CI/CD gate requires Matt's explicit direct verification and approval
before implementation. A gate is a new blocking check, requirement, matrix or
release condition. Agents must not add one on their own: first present the
proposed gate, its reason and its runtime/coverage cost to Matt. Broad permission
to implement or merge does not grant this approval.

Keep automatic verification to backend/security and native core, using one release
toolchain. Each blocking test must name the user failure it prevents and disclose
measured runtime. New jobs, matrices, frameworks or coverage expansion require
explicit scope approval. Keep broader regressions manual. Reuse native results
only for identical source, test policy and toolchain; missing or failed proof must
never authorize release. See [the coverage and release rules](docs/CI.md).
